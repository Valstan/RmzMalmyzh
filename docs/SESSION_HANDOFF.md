🔴 **2026-09-04, инцидент и его закрытие: сутки в админке нельзя было открыть НИ ОДИН
документ.** Нашёл владелец, увидев «Application error» на `/admin/account/`. Причина —
миграция `20260823_000001` (применена 02.09): она создала таблицы `novosti`/`rubriki`, но не
добавила две колонки в **существующую** `payload_locked_documents_rels`. Payload берёт
блокировку при открытии любого документа и перечисляет в запросе все коллекции разом,
поэтому падало редактирование целиком — страницы, заявки, аккаунт, — а списки и дашборд
работали, и поломка выглядела выборочной. В журнале: `column …novosti_id does not exist`.

**Почему проскочило (класс G231, о котором brain предупреждал 07.08).** Заготовку DDL
снимает `dump-schema.yml` **по регулярке имён таблиц** — правка существующей таблицы в
выборку не попадает by design. Дальше файл обёрнут в `IF NOT EXISTS`, и `CREATE TABLE IF NOT
EXISTS payload_locked_documents_rels` стал тихим no-op. Приёмка `apply-migration.yml`
сравнивала **список таблиц**, а он не изменился — dry-run и apply позеленели на неполной
миграции.

**Закрыто (PR #69):** миграция `20260904_000001_locked_documents_rels.sql` (колонки, индексы,
внешние ключи по эталону из `dump-schema`, прогон 33797832306) применена на прод, бэкап
`pre-migration-20260903T194728Z`. Контрмеры: снимок схемы в `apply-migration.yml` теперь по
паре «таблица.колонка» и падает не только на появлении, но и на **пропаже** строк схемы;
в `probe-prod.yml` появились дамп ошибок рендера из журнала и проверка дрейфа «у каждой
коллекции конфига есть своя колонка в `payload_locked_documents_rels`». Проверено вживую:
`/admin/account/` и карточка записи ленты открываются и сохраняются.

## Прод-заметки (стадия 2)

- **Картинки контента:** применение импорта — только `apply-media-import.yml` (dispatch). `dry-run` безопасен, для `apply`/`reset` нужно вписать слово `ПРИМЕНИТЬ`; воркфлоу сам делает `pg_dump` в `shared/backups/` (ротация 10). Порядок фаз обязателен: `media` → доставка файлов → `links`; необратимый шаг последний, поэтому падение середины оставляет прод рабочим (проверено — на этом и упало 28.07). Файлы едут **tar-over-ssh**: `rsync` на боксе не установлен.
- **Записи media без файлов** (не доехала доставка) — прогон падает с диагнозом. Лечение только `mode=reset` + чистый повтор: перезалить файл в ту же запись нельзя, Payload добавит суффикс к имени и сломает поиск по детерминированному имени. `reset` откажется работать, когда контент уже переведён на `/media/` — там откат через `pg_dump`.
- **Проба REST API:** URL писать **со слэшем** и с `curl -L` — при `trailingSlash: true` запрос без слэша отдаёт 301 с телом-путём вместо JSON, и `grep` без совпадений под `set -e` роняет шаг молча. За сессию наступили дважды.
- **Яндекс.Метрика:** счётчик `111854549`, кабинет — аккаунт владельца `ekipagh`. Номер и разметка информера — в `ANALYTICS` (`src/lib/site.ts`), намеренно в коде, а не в env: CI собирает без прод-окружения. Разметку информера **брать только из кабинета** — самосборный URL не несёт `class="ym-advanced-informer"`/`data-cid`, и картинка навсегда остаётся нулевой при честных 200 (G237). После включения информера Метрика пересчитывает его 30–60 минут; нули в этот период — норма, не поломка. Тег на клиенте картинку **не обновляет** — в открытой вкладке останется старая.
- **Миграции схемы (появились 2026-08-23).** DDL снимать только воркфлоу `dump-schema.yml`
  (dispatch, фильтр по именам таблиц): на PC40 нет ни Postgres, ни Docker, а придуманный руками
  DDL ломается уже на проде. Три грабли, на которые наступили в первый же заход:
  - **`pg_dump -t` не выгружает типы.** В дампе стоит `source public.enum_novosti_source`,
    а `CREATE TYPE` отсутствует — миграция проходит чтение глазами и падает на проде.
    `dump-schema.yml` с тех пор печатает типы отдельной секцией всегда.
  - **`workflow_dispatch` запускается только с дефолтной ветки.** Воркфлоу, нужный для работы
    НАД веткой, обязан попасть в `main` раньше самой ветки — иначе `gh workflow run --ref` даёт 404.
  - **`payload migrate` на проде звать нельзя.** После `pushSchema` в `payload_migrations` лежит
    строка `dev` с `batch = -1`; штатный `migrate` задаёт по ней интерактивный вопрос про потерю
    данных и на раннере без TTY тихо выходит с кодом 0. Применять только сырой `.sql` через
    `psql -v ON_ERROR_STOP=1`.
- **Пробы прода с GitHub-раннера дают `status 000`** (http/https/`s_client`) при живом сайте — блокировка снаружи, а не регресс. Диагностику с бокса (`ssh rmz`) в `probe-prod.yml` это не затрагивает.
- Секреты форм: **только** через `apply-form-secrets.yml` (dispatch), не руками. `SMTP_PASS` опционален.
- ⚠️ Пароль приложения Яндекса создавать **под аккаунтом ящика** `valstan@valstan.ru` — иначе `535`.
- `setup-prod-stage2.yml` с `force_restore=true` **сносит контент** — только осознанно.
- Будущие изменения схемы Payload → миграция + применение на проде ДО деплоя (guard #017) + **`.json`-снапшот в том же коммите** (G192, `migrations/` пока нет).
- Postgres на боксе **нативный** (`sudo -u postgres psql`, `localhost:5432`); `docker exec … psql` в воркфлоу — это CI-сервис, не бокс. Прогнать `payload run` против прода можно через туннель `ssh -f -N -L 15432:127.0.0.1:5432 rmz`.
