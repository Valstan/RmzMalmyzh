# Грабля стека Payload: `payload run script.ts` + `run().catch()` = молчаливый no-op

## Что случилось (RmzMalmyzh, 2026-07-17)

Сид стадии 2 (`src/seed/seedFromStage1.ts`, 128 страниц) был написан как

```ts
const run = async () => { /* payload.create × 128 */ }
void run()
```

`corepack pnpm payload run src/seed/seedFromStage1.ts` отработал **с exit 0 и без единой строки вывода** — и ничего не записал. CLI завершает процесс после импорта модуля, не дожидаясь висящего промиса.

Дальше это уехало на прод: setup-воркфлоу собрал `pg_dump` эфемерной CI-базы (в дампе был только админ), restore на боксе честно отрапортовал «дамп применён», и прод-БД оказалась пустой. Поймали по строчке `страниц в БД — 0`, которую печатал сам воркфлоу; смоук `/` при этом был бы зелёным (главная отдаёт 200 и с пустой БД).

Починка: top-level `await run()` + жёсткие страховки `[ "$N" -ge 100 ]` после сида в CI и после restore на боксе.

## Почему шлю (переносимость)

В **SabantuyMalmyzh** тот же паттерн живёт в двух скриптах:

- `web/src/seed/collectVkCandidates.ts:199` — `run().catch((e) => {...})`
- `web/src/seed/moderateVkCandidates.ts:61` — то же

Оба запускаются через `payload run` и, если внутри есть await'ы дольше момента импорта, могут так же тихо не доработать до конца (частичный результат + exit 0). Остальные сиды Сабантуя написаны top-level-стейтментами с `process.exit(0)` в конце — они безопасны. В KazanskayaMalmyzh проблемных скриптов не нашёл.

## Что предлагаю (recommend)

1. В экосистемном правиле по Payload-сидам зафиксировать: **entry-point скрипта под `payload run` — только top-level `await`** (или `await run()`), никогда `void run()` / `run().catch()`.
2. Точечно посмотреть два скрипта Сабантуя выше (VK-кандидаты — не критичный путь, но результат может быть молча неполным).
3. Общий принцип, который тут сработал лучше смоука: **воркфлоу, наполняющий данные, должен сам проверять количество** (`count >= N`), а не полагаться на HTTP-200 — фронт с пустой БД выглядит здоровым.

## Смежная мелочь (для копилки CI)

`pg_dump` на ubuntu-раннере — версия 16, сервис-контейнер `postgres:17` → `server version mismatch`, а `postgresql-client-17` через apt не ставится (нет pgdg-репо). Рабочее решение без возни с репозиториями:

```yaml
docker exec ${{ job.services.postgres.id }} pg_dump -U postgres -d <db> --no-owner --no-privileges > dump.sql
```

Версия клиента совпадает с сервером по построению.
