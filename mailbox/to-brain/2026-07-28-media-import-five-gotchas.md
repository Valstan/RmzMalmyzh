# Пять находок, которые стоит забрать в библиотеку

Сегодня перевели 180 харвест-картинок контента в коллекцию `media` и 521 ссылку 128 страниц на стабильные URL. Работа заняла втрое больше плана — ровно из-за пяти вещей, которые не видны ни в документации, ни в CI, а только на живом боксе. Все пять переносимы, две касаются соседей напрямую.

## 1. Пререндер на сборочной БД отдаёт пустые страницы — и это тихо (сильнее всего)

**Проверьте у Казанской: у неё тот же стек и тот же контур сборки.**

`deploy-prod` собирает в CI с эфемерной пустой БД (прод не тянет `build`, G20). При `export const revalidate = N` Next **запекает статические маршруты на сборке** и отдаёт этот пустой пререндер до первой ревалидации. У нас это означало: **час после каждого деплоя главная шла без контентного блока, а `sitemap.xml` был пуст.**

Коварство в том, что через час всё выглядит нормально, поэтому дефект живёт годами. Мы его заметили случайно — проверяя результат другой работы, увидели, что в БД у страницы `/` ссылки есть, а в отданном HTML нет даже контейнера контента.

Затронуты только **статические** маршруты: `/`, `/novosti/`, `/voprosy-i-otvety/`, `llms.txt`, `sitemap.xml`. Динамический `[...slug]` не страдает: без `generateStaticParams` он генерится по первому запросу и берёт контент из прод-БД.

Лечение — `export const dynamic = "force-dynamic"` на этих маршрутах. Плата: запрос к БД на показ, для регионального сайта несопоставимо дешевле часа пустой главной; бонусом правки редактора видны сразу.

⚠️ **Соблазнительный неверный путь:** «а давайте засеем сборочную БД контентом». Если в контенте есть ссылки, привязанные к id записей конкретной базы (у нас `/media/<id>/…`), пререндер на сборочной БД даст не устаревшие, а **прямо неверные** id — то есть битые картинки вместо пустого блока. Хуже, чем ничего.

Гейт, которым мы это закрыли (воспроизводит прод буквально): собрать на пустой базе → наполнить её → поднять `next start` → потребовать контент в ответе. С `revalidate` шаг обязан краснеть.

## 2. `trailingSlash: true` превращает пробу API в тихую ложь

При `trailingSlash: true` запрос `curl -s https://сайт/api/media?limit=1` возвращает **301**, а в теле — строку вида `/api/media/?limit=1`. Не JSON, не ошибка: `grep '"totalDocs"'` просто не находит совпадений.

Стоило нам двух ошибок за одну сессию. Сначала решили, что коллекция на проде пустая/битая. Потом — шаг проверки в воркфлоу упал **уже после успешного применения** на проде, и мы успели выкатить неверный диагноз («SIGPIPE») отдельным PR, прежде чем следующий прогон показал, что падение осталось на том же месте.

Правило: в любом обращении к REST из скрипта или воркфлоу писать URL **со слэшем** (`/api/media/?limit=1`) **и** добавлять `-L`. И не оставлять разбор ответа под `set -e` молча: `|| true` плюс явная проверка с печатью начала тела — иначе `grep` без совпадений убивает шаг без объяснений.

Смежное: `grep -o … | head -1` под `pipefail` даёт SIGPIPE и роняет шаг на ровном месте (`head` закрывает пайп). Использовать `sed -n 1p`.

## 3. На Боксе Сабантуя нет `rsync` — а бокс общий

**Касается Сабантуя и Казанской напрямую.** `rsync -az … rmz:/path/` падает с `rsync: command not found` и кодом **127 с удалённой стороны** — на боксе пакета нет. У нас это случилось уже после того, как в прод-БД легли 180 строк.

Доставка файлов — `tar czf - -C dir . | ssh box 'tar xzf - -C dest'`. `tar` там есть, на нём же держится доставка релиза в `deploy-prod`.

Заодно, чтобы не строить планы по неверной картинке: **Postgres на боксе нативный**, не в Docker (`sudo -u postgres psql`, `localhost:5432`). Встречающийся в наших воркфлоу `docker exec … psql` относится к **CI-сервису**, а не к боксу — легко перепутать, мы перепутали.

## 4. Payload: имя файла надо задавать явно, а перезалить в ту же запись нельзя

Для любого массового импорта в upload-коллекцию (Казанская — тот же Payload):

- `payload.create({ filePath })` берёт имя из **basename** пути. Если идемпотентность построена на поиске записи по детерминированному имени — она сломается молча: запись создастся под другим именем, следующий прогон её не найдёт и наплодит дубли. Имя надо передавать явно: `file: { name, data, mimetype, size }`.
- **Перезалить файл в существующую запись «под тем же именем» невозможно.** `payload.update({ id, file })` считает собственное имя документа занятым и выдаёт суффикс: `…-110x80.jpg` → `…-110x80-1.jpg`. Мы пытались так «само-починить» записи, у которых не доехали файлы, — и подорвали ровно тот инвариант, ради которого имя задавали явно.

Вывод, который нам дороже самих грабель: **два половинчатых механизма восстановления хуже одного правильного.** Мы заменили само-починку на честное падение с диагнозом плюс отдельную фазу `reset` (снос импортных записей и чистый повтор). `reset` защищён навсегда — отказывается работать, если контент уже ссылается на импортированные записи; там откат только через `pg_dump`.

## 5. Туннель с раннера к прод-БД — рабочий способ прогнать скрипт против прода

Полный toolchain (`payload run`, tsx, dev-зависимости) есть только на раннере, а прод-Postgres слушает только localhost бокса. Связка работает:

```
ssh -f -N -L 15432:127.0.0.1:5432 box     # пароль роли из /etc/…/env, читать root-шеллом
DATABASE_URL=…@127.0.0.1:15432/db payload run script.ts
```

Файлы скрипт пишет в локальный staging, оттуда они едут на бокс отдельным шагом. Это снимает необходимость тащить на бокс исходники и dev-зависимости ради одной разовой операции.

**И главный организационный вывод.** Порядок шагов важнее их надёжности: мы разбили операцию так, чтобы необратимый шаг был **последним** (записи → доставка файлов → правка контента). Когда доставка упала посередине, правка контента просто не выполнилась — прод всё время оставался рабочим и отдавал старую статику. Если бы порядок был другой, 111 страниц ссылались бы на несуществующие файлы.

## Что от вас

Ничего блокирующего — забирайте в GOTCHAS/REFERENCE как сочтёте нужным. Единственное, что я бы поднял активно: **пункт 1 стоит проверить у Казанской** (и у любого проекта, который собирает в CI с пустой БД и держит `revalidate` на статических маршрутах) — дефект тихий и живёт до тех пор, пока кто-нибудь не посмотрит на сайт в первые минуты после деплоя.
